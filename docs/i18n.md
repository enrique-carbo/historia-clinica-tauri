# 🌍 Internacionalización (i18n) — diseño y plan

Estado: **preparación** (2026-10-31). No se implementa todavía: la app es
para Argentina y el principio rector es "Core mínimo, nada por si acaso".
La decisión tomada es **dejar la puerta abierta y arrancar por lo barato**,
para que el día que haya un segundo mercado concreto el trabajo sea
incremental y no un rediseño.

## Decisión

- **No** meter un framework de i18n ni traducir la UI hoy.
- **Sí** documentar el mapa de texto, adoptar convenciones que no cuestan
  nada en código nuevo, y priorizar el paso que rinde solo: errores del
  backend como **códigos estables** en vez de mensajes crudos.
- **Disparador** para ejecutar las fases: un mercado/idioma concreto
  (cliente fuera de Argentina o apuesta comercial explícita a vender
  afuera). Sin disparador, esto queda como backlog.

## Mapa del texto visible (medido 2026-10-31)

| Capa | Dónde | Cómo está hoy | Costo de traducir |
|---|---|---|---|
| UI React | `src/**/*.tsx` | Strings embebidos en JSX | Medio (mecánico) |
| Errores del backend | `src-tauri/src/commands/*.rs` (~28) | Strings listos, mostrados **crudos** en ~26 lugares (`❌ Error: ${err}`) | Medio — y hoy además son inconsistentes |
| Labels del schema | `profiles/{med,vet}/entity_schema.json` | **Data-driven** (labels en el JSON del perfil) | Bajo: agregar variantes por locale, no refactor |
| Export Markdown | `src-tauri/src/export/render.rs` (~200 literales) | Formato fijo, español | Medio-alto |
| Fechas | `src/utils/dateUtils.ts` | `es-AR` hardcodeado en **un solo punto** | Bajo: parametrizar ahí |

## Principios

1. **i18n es ortogonal a los perfiles**: la matriz es *producto* (Med/Vet)
   × *idioma*, no un perfil nuevo. Un toggle de idioma no debe tocar
   `build.rs` ni duplicar builds.
2. **El texto legal no se traduce automáticamente**: consentimiento,
   avisos y cumplimientos (Ley 26.529) requieren revisión humana por
   jurisdicción. Se traducen como contenido, no como string de UI.
3. **Los datos clínicos no se traducen nunca**: solo el "chrome" (labels,
   botones, mensajes). Lo que escribe el profesional se queda como está.
4. **La firma del export no cambia**: cubre los bytes del Markdown emitido;
   un export en otro idioma produce otro hash (esperado y correcto), los
   exports viejos siguen verificando.
5. **Sin auto-traducción en runtime**: diccionarios estáticos, sin APIs de
   traducción (offline-first, datos de salud).

## Fases (en orden, cada una útil por sí sola)

### Fase 0 — Convenciones (sin costo, cuando se toque código nuevo)
- [ ] Strings nuevos de UI, en lo posible, centralizados en `src/i18n/`
      con `t("clave")` tipado (diccionario `es.ts` con `as const`).
- [ ] Commands nuevos: devolver **códigos de error estables** +
      parámetros (`ERR_...`), no frases. El frontend mapea a texto.
- [ ] No agregar listas de labels hardcodeadas en componentes: el schema
      y `config/entry_templates/` ya son la fuente única.

### Fase 1 — Infraestructura de UI
- [ ] `src/i18n/`: diccionario tipado + hook `useT()`; locale activo en
      settings persistido (default: `es-AR`).
- [ ] Migración incremental: se empieza por `Navbar`, `EmptyState`,
      `Button`, mensajes del sistema; el resto cuando toque.
- [ ] Fechas/números vía `Intl` con el locale activo (`dateUtils` ya es el
      único punto; el widget Día/Mes/Año ya es numérico).
- [ ] Tests: seleccionar por rol/label accesible, no por texto literal
      (evita diccionarios rotos). Los tests de invariantes se mantienen.

### Fase 2 — Backend
- [ ] `commands/*.rs`: errores como códigos (`ERR_...`) + campos; el
      frontend traduce. Beneficio inmediato aunque nunca haya i18n:
      mensajes consistentes y testeables.
- [ ] Export (`render.rs`): labels del reporte derivados del schema/perfil
      por locale, en vez de literales.

### Fase 3 — Schema por locale
- [ ] `entity_schema.json`: variantes de `label` por locale (o overlay
      `i18n/{locale}.json` por perfil). El frontend resuelve según el
      locale activo; el backend sigue usando el schema base.

### Fase 4 — Documentación
- [ ] `docs/guia-usuario.md` por idioma **solo si hay mercado**.
- [ ] README/AGENTS quedan en español técnico (dev-facing): no son texto
      de producto.

## Riesgos y deuda

- **Tests acoplados a labels**: hoy algunos esperan texto literal; al
  migrar, pasar a roles/`aria-label` estables.
- **Legalese**: cualquier traducción legal necesita revisión humana.
- **Bundle**: un diccionario propio pesa KB; `react-i18next` solo si
  aparecen plurales/formatos complejos (evaluar también el futuro mobile).
- **RTL**: no urge (mercados objetivo son LTR); si se planifica árabe/hebreo,
  usar propiedades lógicas (`ms-*`/`me-*`) al agregar CSS nuevo.
